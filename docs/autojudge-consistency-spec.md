# AutoJudge для оценки непротиворечивости агентной памяти

## Цель

Использовать AutoJudge как offline validation layer (слой офлайн-валидации) для оценки результатов retrieval (поиска) в IMCA.

AutoJudge не заменяет retrieval и не участвует в выполнении агента. Он используется после retrieval для оценки того, является ли полученный контекст памяти семантически непротиворечивым и достаточным для ответа.

Это соответствует предложению использовать AutoJudge для offline validation (офлайн-валидации), а не сразу встраивать его в online agent pipeline (онлайн-конвейер агента).

## Почему обычных retrieval-метрик недостаточно

В текущих экспериментах используются:

- Hit@5;
- Recall@5;
- invalid result slots (невалидные результаты по времени).

Однако анализ HaluMem показал, что факт может находиться за пределами strict query-time slice (жёсткого временного среза), но всё равно быть необходимым для ретроспективного рассуждения.

Например, более поздний факт может позволять установить, что событие ещё не произошло к более ранней дате.

Поэтому необходимо различать:

- настоящий конфликт;
- корректное изменение состояния во времени;
- полезный факт вне временного среза;
- вредный stale fact (устаревший факт);
- отсутствие необходимого evidence (свидетельства).

## Пилотный набор

Первый пилотный набор состоит из 27 кейсов HaluMem `Memory Conflict`, где:

- flat BM25 успешен по Hit@5;
- strict temporal retrieval теряет reference evidence.

Эти случаи уже были отдельно проанализированы в рамках consistency error analysis.

## Retrieval policies для сравнения

Для одних и тех же кейсов можно сравнивать результаты:

1. flat BM25;
2. strict temporal;
3. permissive query-aware;
4. transition-aware;
5. before-aware.

Важно, что AutoJudge в этой постановке оценивает уже готовый retrieval output (результат поиска), а не заменяет сам retrieval.

## Таксономия для оценки

### `consistent`

Полученные факты совместимы между собой и достаточны для временного контекста вопроса.

### `true_conflict`

В retrieval одновременно присутствуют несовместимые утверждения, относящиеся к одному объекту, свойству, контексту и релевантному времени.

### `temporal_update`

Факты имеют разные значения, но относятся к разным временным периодам и описывают корректное изменение состояния.

### `stale_but_relevant`

Факт находится за пределами strict query-time slice, но необходим как историческое или контрастное evidence для ответа.

### `stale_and_harmful`

Факт находится за пределами временного среза, не требуется для рассуждения и потенциально может привести к неправильному ответу.

### `missing_required_evidence`

Retrieval не содержит информации, необходимой для корректного ответа.

### `insufficient_information`

Имеющегося контекста недостаточно, чтобы уверенно определить характер временного отношения или противоречия.

## Предлагаемый результат оценки

Для каждого кейса AutoJudge должен возвращать структурированную оценку со следующими полями:

- `consistency_status`: consistent / conflicting / underdetermined;
- `conflict_type`: none / true_conflict / temporal_update;
- `out_of_slice_evidence`: none / relevant / harmful;
- `missing_required_evidence`: true / false;
- `supports_answer`: true / false;
- `confidence`: численная уверенность;
- `reason`: краткое объяснение решения.

## Что передаётся AutoJudge

Для каждого retrieval run (запуска поиска) формируется trace (трасса), содержащая:

- исходный вопрос;
- название retrieval policy;
- retrieved memory items;
- временные метаданные;
- reference evidence;
- диагностические признаки, полученные в предыдущем анализе.

## Режим использования

Для первого эксперимента AutoJudge рассматривается как offline validation layer.

Все 27 кейсов относятся к одной задаче и используют одну и ту же таксономию оценки. Это позволяет применять единый judge setup ко всем retrieval policies и сравнивать их при одинаковых условиях.

## Ограничение

Результат AutoJudge не рассматривается как автоматический ground truth.

Он используется как дополнительная семантическая оценка к уже имеющимся retrieval-метрикам.

Цель такого анализа — проверить, действительно ли формально out-of-slice результаты являются вредными, или некоторые из них необходимы для корректного временного рассуждения.
