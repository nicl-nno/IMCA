# Минимальный пример использования AutoJudge для временной агентной памяти

## Задача

Мы используем AutoJudge для семантической оценки результатов поиска
в агентной памяти.

Нас интересует ситуация, когда факт находится вне строгого временного
среза, но всё равно необходим для ответа на вопрос.

Пример взят из HaluMem Memory Conflict.

## Вопрос

> Did Martin officially begin his retirement on June 1, 2028?

То есть:

> Начал ли Martin официально свою пенсию 1 июня 2028 года?

Эталонное свидетельство бенчмарка:

> Martin officially started his sabbatical on June 1, 2028.

Следовательно, 1 июня начался sabbatical (саббатикал), а не retirement
(выход на пенсию).

---

## Вариант 1. Strict temporal retrieval

Строгая временная фильтрация возвращает только факты,
активные в выбранный момент времени.

Факт про начало sabbatical 1 июня оказывается вне строгого временного
среза и не попадает в top-5.

В найденном контексте остаются, например, сведения о том, что Martin
рассматривал возможность раннего выхода на пенсию.

Проблема:

контекст непротиворечивый, но его недостаточно, чтобы установить,
начал ли Martin пенсию именно 1 июня.

Ожидаемая семантическая оценка:

- consistency_status: consistent
- conflict_type: none
- out_of_slice_evidence: none
- missing_required_evidence: true
- supports_answer: false

---

## Вариант 2. Query-aware retrieval

Поиск с учётом семантики вопроса допускает добавление релевантного факта
вне строгого временного среза.

В top-5 попадает:

> Martin officially started his sabbatical on June 1, 2028.

Этот факт находится вне строгого временного среза, но непосредственно
помогает ответить на вопрос: указанное событие было sabbatical,
а не retirement.

В текущем фиксированном AutoJudge evaluator v2 получено:

- consistency_status: consistent
- conflict_type: none
- out_of_slice_evidence: relevant
- missing_required_evidence: false
- supports_answer: true
- confidence: 0.9

Таким образом, факт вне временного среза оказался не вредным stale-фактом,
а полезным свидетельством для ответа.

---

## Почему этот пример интересен

Если оценивать систему только количеством фактов вне временного среза,
query-aware retrieval выглядит хуже строгой временной фильтрации.

Но семантически ситуация обратная:

- strict temporal retrieval сохраняет временную чистоту контекста,
  но теряет необходимое свидетельство;
- query-aware retrieval допускает один факт вне среза,
  который делает ответ возможным.

Поэтому для оценки временной агентной памяти недостаточно только
формальных temporal-метрик. Требуется семантическая проверка того,
является ли такой факт релевантным или вредным.

---

## Что обнаружилось при использовании AutoJudge

Во время пилота проявились два важных момента.

### 1. Динамический набор judges

Если PoolGenerator запускается отдельно для каждой retrieval policy,
он создаёт разные наборы judges.

В результате одновременно меняются:

- способ поиска;
- состав evaluator.

Поэтому такие результаты нельзя напрямую сравнивать между собой.

Для эксперимента мы перешли к фиксированному набору:

- CONSISTENCY_JUDGE — проверка непротиворечивости;
- TEMPORAL_JUDGE — проверка временных отношений;
- EVIDENCE_JUDGE — проверка достаточности свидетельств;
- OUT_OF_SLICE_JUDGE — оценка фактов вне временного среза;
- FINAL_AGGREGATOR — итоговое объединение оценок.

### 2. Разделение retrieved evidence и reference evidence

Если явно не разделить факты, найденные системой, и эталонные свидетельства
бенчмарка, evaluator иногда начинает:

- считать reference evidence частью retrieval;
- классифицировать reference evidence как out-of-slice;
- воспринимать вопрос как фактическое утверждение и искать конфликт
  между вопросом и найденными фактами.

Поэтому во второй версии протокола мы явно фиксируем:

- retrieved memory — только факты, реально возвращённые системой;
- reference evidence — используется только для проверки достаточности;
- query — это вопрос, а не утверждение и сам по себе не может быть
  источником противоречия.
