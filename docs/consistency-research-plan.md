# Исследование временной непротиворечивости памяти

## Общий исследовательский вопрос

Как системе агентной памяти отличать корректные временные изменения состояния от вредных противоречий, не теряя при этом информацию, необходимую для ретроспективного рассуждения?

Текущий временной адаптер IMCA использует фильтрацию по времени, чтобы исключать утверждения, которые считаются невалидными на интерпретируемый момент запроса.

Анализ на HaluMem показал, что такой подход хорошо устраняет устаревшие результаты, но в некоторых случаях жёсткая фильтрация по одному временному срезу также удаляет информацию, необходимую для ответа.

---

# H1. Жёсткая фильтрация по временному срезу может удалять необходимую информацию

## Гипотеза

Strict temporal filtering (жёсткая временная фильтрация) удаляет устаревшие элементы памяти, однако некоторые вопросы требуют информации, находящейся за пределами интерпретируемого временного среза.

Следовательно, отсутствие stale results (устаревших результатов) само по себе не означает, что retrieval (поиск) оптимален для временного рассуждения.

## Benchmark

HaluMem-Medium.

Основной анализ проводится на подмножестве:

- `Memory Conflict`.

## Baselines

Сравниваются:

- flat BM25 retrieval - поиск без временной фильтрации;
- strict temporal retrieval - текущий временной baseline IMCA.

## Метрики

Используются:

- Hit@5;
- Recall@5;
- invalid result slots - число результатов, невалидных на интерпретируемый момент запроса;
- paired wins/losses - количество случаев, где один метод выигрывает или проигрывает другому.

## Эксперимент

Были проанализированы случаи, в которых:

- flat retrieval успешно находит reference evidence;
- strict temporal retrieval его теряет.

## Результат

Для `Memory Conflict`:

- flat Hit@5: 84.92%;
- strict temporal Hit@5: 83.22%;
- strict temporal invalid slots: 0.

Обнаружено 27 случаев, где flat retrieval успешен по Hit@5, а strict temporal retrieval - нет.

Из них:

- в 24 из 27 случаев reference evidence имеет timestamp позже даты, извлечённой из вопроса;
- 3 случая связаны с явными replacement/update links;
- 1 случай содержит временной интервал нулевой длины.

Дополнительно 27 случаев были разделены простой эвристикой по формулировке вопроса:

- 17 - transition / retrospective;
- 10 - state-at-time.

## Интерпретация

Дата, указанная в вопросе, не всегда может использоваться как жёсткий cutoff (временную границу) для памяти.

Для части ретроспективных вопросов более поздняя информация необходима, чтобы определить, произошло ли событие до указанной даты.

Пример:

> Did Donna establish EcoStrategic Consulting before March 01, 2038?

Reference evidence сообщает, что компания была запущена 1 июля 2038 года.

Хотя этот факт относится к более позднему моменту, именно он позволяет установить, что к 1 марта событие ещё не произошло.

## Вывод по H1

Полученные результаты поддерживают гипотезу: strict temporal filtering полностью устраняет невалидные временные результаты, но в отдельных ретроспективных случаях вместе с ними удаляет необходимый evidence.

---

# H2. Политика временного retrieval должна зависеть от семантики запроса

## Гипотеза

Одна и та же temporal retrieval policy (политика временного поиска) не подходит для всех типов временных вопросов.

В частности, поведение retrieval может зависеть от направления временного отношения, выраженного в запросе.

## Benchmark

HaluMem-Medium.

Основное подмножество:

- `Memory Conflict`.

Дополнительно отдельно анализировались вопросы с `before` и `after`.

## Baseline

Strict temporal retrieval.

## Проверенные варианты

Были реализованы и проверены четыре варианта:

1. permissive query-aware retrieval;
2. explicit-update transition-aware retrieval;
3. direction-aware retrieval;
4. conservative before-aware retrieval.

---

## Вариант 1. Permissive query-aware retrieval

Для transition / retrospective вопросов метод сохраняет четыре результата strict temporal retrieval и допускает один дополнительный кандидат за пределами временного среза.

### Результат на Memory Conflict

- strict temporal Hit@5: 83.22%;
- query-aware Hit@5: 84.14%;
- query-aware Recall@5: 70.40%;
- wins относительно strict temporal: 12;
- losses: 5;
- invalid slots: 233.

## Интерпретация

Метод возвращает часть потерянной информации и повышает Hit@5, но слишком сильно ослабляет временные ограничения и возвращает большое число невалидных результатов.

---

## Вариант 2. Explicit-update transition-aware retrieval

Во втором варианте дополнительный факт разрешался только в том случае, если он участвовал в явной old/new replacement relation, извлечённой из `original_memories`.

### Результат на Memory Conflict

- strict temporal Hit@5: 83.22%;
- transition-aware Hit@5: 82.83%;
- transition-aware Recall@5: 69.38%;
- wins: 3;
- losses: 6;
- invalid slots: 274.

## Интерпретация

Такое ограничение оказалось слишком жёстким.

Результат согласуется с анализом 27 ошибок: только 3 из них были связаны с явными replacement/update links, поэтому этих связей недостаточно, чтобы описать большинство проблемных случаев.

---

## Вариант 3. Direction-aware retrieval

В третьем варианте отдельно учитывалось направление временного отношения `before` и `after`.

Внешний кандидат мог заменить пятый strict temporal результат только если:

- его временное направление соответствовало вопросу;
- BM25 ранжировал его выше вытесняемого временно валидного результата.

### Общий результат

- strict temporal Hit@5: 74.95%;
- direction-aware Hit@5: 74.88%;
- strict Recall@5: 60.02%;
- direction-aware Recall@5: 59.90%;
- wins: 1;
- losses: 3;
- invalid slots: 114.

### Memory Conflict

- strict temporal Hit@5: 83.22%;
- direction-aware Hit@5: 83.22%;
- strict Recall@5: 70.87%;
- direction-aware Recall@5: 70.57%;
- wins: 1;
- losses: 1;
- invalid slots: 64.

### Вопросы с `before`

Количество вопросов: 26.

- strict Hit@5: 80.77%;
- direction-aware Hit@5: 84.62%;
- strict Recall@5: 73.08%;
- direction-aware Recall@5: 76.92%;
- wins: 1;
- losses: 0;
- invalid slots: 4.

### Вопросы с `after`

Количество вопросов: 579.

- strict Hit@5: 71.33%;
- direction-aware Hit@5: 70.81%;
- strict Recall@5: 51.63%;
- direction-aware Recall@5: 50.91%;
- wins: 0;
- losses: 3;
- invalid slots: 110.

## Интерпретация

Одинаковое ослабление temporal filtering для `before` и `after` работает по-разному.

На `before` наблюдается улучшение без потерь, а на `after` - ухудшение.

Это показывает асимметрию между двумя направлениями временного отношения.

---

## Вариант 4. Conservative before-aware retrieval

На основании результатов direction-aware эксперимента временное ослабление было оставлено только для вопросов с явным `before`.

Для всех остальных вопросов сохраняется strict temporal retrieval.

### Общий результат

- strict temporal Hit@5: 74.95%;
- before-aware Hit@5: 74.99%;
- strict Recall@5: 60.02%;
- before-aware Recall@5: 60.06%;
- wins: 1;
- losses: 0;
- invalid slots: 4.

### Memory Conflict

- strict temporal Hit@5: 83.22%;
- before-aware Hit@5: 83.36%;
- strict Recall@5: 70.87%;
- before-aware Recall@5: 71.00%;
- wins: 1;
- losses: 0;
- invalid slots: 2.

### Вопросы с `before`

- strict Hit@5: 80.77%;
- before-aware Hit@5: 84.62%;
- strict Recall@5: 73.08%;
- before-aware Recall@5: 76.92%;
- wins: 1;
- losses: 0;
- invalid slots: 4.

## Интерпретация

Before-aware вариант является наиболее аккуратной из проверенных эвристик.

Он немного улучшает Hit@5 и Recall@5 относительно strict temporal baseline и не теряет ни одного ранее успешного Hit@5 случая.

При этом эффект сосредоточен на небольшом подмножестве: явных `before` вопросов только 26 из 2639 вопросов с evidence.

Поэтому полученный результат нельзя интерпретировать как общее улучшение temporal retrieval на всём benchmark.

Он показывает более узкий эффект: для некоторых ретроспективных `before` вопросов жёсткий временной срез оказывается слишком ограничивающим.

---

# Итог по проверенным гипотезам

## H1

Поддерживается текущими результатами.

Strict temporal filtering устраняет невалидные временные результаты, но в части ретроспективных вопросов удаляет evidence, необходимый для ответа.

## H2

Получила предварительное подтверждение в более узкой форме.

Эксперименты показывают, что временная политика retrieval зависит от семантики и направления запроса.

Особенно заметный эффект обнаружен для явных `before` вопросов.

При этом расширение этого правила на `after` вопросы ухудшает результат, поэтому единая симметричная политика для двух направлений не подтверждается.

---

# Ограничение внешнего сравнения

HaluMem публикует результаты других memory-систем на `Memory Conflict`, однако эти результаты относятся к end-to-end QA accuracy.

В текущих экспериментах IMCA измеряются retrieval Hit@5, Recall@5 и temporal validity.

Поэтому напрямую сравнивать опубликованные QA-результаты других систем с текущими retrieval-результатами IMCA некорректно: это разные уровни evaluation pipeline.

---

# Практический смысл исследования

Практическая задача состоит не только в улучшении retrieval-метрик.

Для агента, работающего с долговременной памятью, важно одновременно:

- не использовать устаревший факт как актуальный;
- не считать нормальное изменение состояния противоречием;
- не удалять более позднюю информацию, если она необходима для ретроспективного ответа;
- не добавлять в контекст лишние конфликтующие версии;
- возвращать такой набор фактов, которого достаточно для принятия решения или ответа агента.

Таким образом, задача состоит в поиске баланса между temporal consistency
(временной согласованностью) и evidence sufficiency
(достаточностью свидетельств).

Практически это должно снижать два типа ошибок агента:

1. ответ на основе устаревшего или противоречивого состояния памяти;
2. невозможность ответить из-за слишком жёсткой фильтрации полезных фактов.

---

# H3. Семантическая оценка retrieval позволяет различать полезный out-of-slice evidence и вредные противоречия

## Гипотеза

Одинаковое наличие фактов за пределами временного среза не означает одинаковую ошибку.

Out-of-slice evidence может быть:

- полезным для ретроспективного рассуждения;
- нейтральным;
- вредным, если создаёт реальное противоречие.

Поэтому одной Hit@5 / Recall@5 оценки недостаточно:
необходимо дополнительно учитывать семантическую роль найденных фактов.

## Метод

Для семантической оценки использовался AutoJudge.

Был зафиксирован один и тот же набор специализированных оценщиков:

- `CONSISTENCY_JUDGE`;
- `TEMPORAL_JUDGE`;
- `EVIDENCE_JUDGE`;
- `OUT_OF_SLICE_JUDGE`;
- `FINAL_AGGREGATOR`.

Для всех retrieval policies использовались одинаковые инструкции
и одна judge-модель `glm-5.3-flash`.

Retrieval policy не передавалась оценщикам напрямую.

## Репрезентативная выборка

Из 27 ошибок strict temporal retrieval были выбраны 5 кейсов,
покрывающих разные failure modes:

- case 001 - transition / retrospective + evidence after question time;
- case 007 - state-at-time + evidence after question time;
- case 009 - transition / retrospective + expired evidence;
- case 010 - expired evidence + zero-length interval;
- case 027 - state-at-time + dated event after question time.

Для каждого кейса сравнивались:

- `before_aware`;
- `flat_bm25`;
- `query_aware`;
- `strict_temporal`;
- `transition_aware`.

Всего выполнено 25 оценок.

## Результат

Количество кейсов, где retrieved context был признан достаточным для ответа:

| Retrieval policy | Supports answer |
|---|---:|
| `flat_bm25` | 5/5 |
| `query_aware` | 3/5 |
| `before_aware` | 2/5 |
| `strict_temporal` | 2/5 |
| `transition_aware` | 2/5 |

## Интерпретация

Результат подтверждает исходную проблему strict temporal filtering,
но показывает, что простого query-aware ослабления недостаточно.

`query_aware` помогает на части retrospective-кейсов,
однако в других случаях не извлекает необходимый факт.

`flat_bm25` чаще сохраняет достаточный evidence,
но иногда вместе с полезными фактами возвращает конфликтующие версии.

Это показывает, что следующий шаг должен учитывать
не только положение факта относительно временного среза,
но и его семантическую роль для конкретного вопроса.

## Вывод по H3

Полезность out-of-slice evidence зависит от содержания факта и типа вопроса.

Следовательно, задача temporal retrieval не сводится
к выбору между строгой и ослабленной временной фильтрацией:
необходим механизм семантической проверки кандидатов.

# Дополнительный эксперимент: организация pipeline проверок

Помимо качества retrieval отдельно рассматривается вопрос о том, как организация специализированных проверок влияет на итоговую оценку retrieved context.

Были сравнены два варианта:

1. parallel pipeline - специализированные judges независимо анализируют один и тот же retrieved context, после чего их результаты объединяет `FINAL_AGGREGATOR`;
2. sequential pipeline - результаты предыдущих специализированных проверок передаются следующим этапам и могут использоваться как дополнительный контекст.

## Parallel baseline

В parallel-варианте:

`CONSISTENCY_JUDGE`, `TEMPORAL_JUDGE`, `EVIDENCE_JUDGE`
и `OUT_OF_SLICE_JUDGE` выполняют независимые оценки,
после чего `FINAL_AGGREGATOR` объединяет их выводы.

## Sequential experiment

Sequential-вариант был проверен на тех же 5 репрезентативных HaluMem-кейсах и тех же 5 retrieval policies.

Для корректного сравнения сохранялись:

- те же исходные traces;
- тот же набор judges;
- те же инструкции;
- модель `glm-5.3-flash`;
- одинаковый формат итогового verdict.

Всего выполнено 25 sequential-оценок.

## Результаты

По признаку `supports_answer` результаты parallel и sequential pipeline совпали:

| Retrieval policy | Parallel | Sequential |
|---|---:|---:|
| `flat_bm25` | 5/5 | 5/5 |
| `query_aware` | 3/5 | 3/5 |
| `before_aware` | 2/5 | 2/5 |
| `strict_temporal` | 2/5 | 2/5 |
| `transition_aware` | 2/5 | 2/5 |

Таким образом, на текущей выборке sequential pipeline не улучшил evidence sufficiency.

При этом в отдельных случаях изменились semantic verdicts.

Например, для `halumem-memory-conflict-027` с `query_aware` parallel pipeline определил:

- `consistency_status = conflicting`;
- `conflict_type = true_conflict`;

а sequential pipeline:

- `consistency_status = consistent`;
- `conflict_type = none`.

При этом в обоих случаях:

- `missing_required_evidence = true`;
- `supports_answer = false`.

То есть изменение организации judges может влиять на интерпретацию retrieved context, но не устраняет проблему отсутствующего evidence.

Также в некоторых оценках сохраняется сочетание:

- `consistency_status = conflicting`;
- `conflict_type = temporal_update`.

Это показывает, что sequential pipeline сам по себе не устраняет неоднозначность между legitimate temporal update и true conflict.

## Вывод

На текущей небольшой выборке нельзя говорить о преимуществе sequential pipeline над parallel.

Sequential-вариант не изменил способность retrieval-политик предоставлять достаточный контекст для ответа, однако повлиял на отдельные semantic classifications.

Поэтому этот эксперимент рассматривается как дополнительный архитектурный анализ, а не как отдельная основная гипотеза исследования.
