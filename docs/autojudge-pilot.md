# Пилотная офлайн-валидация с AutoJudge

## Цель

Использовать AutoJudge как дополнительный семантический оценщик для проверки
качества временного поиска в агентной памяти.

Основная проблема обычных метрик поиска состоит в том, что факт,
находящийся вне строгого временного среза, может быть либо действительно
устаревшим и вредным, либо, наоборот, необходимым для ответа на
ретроспективный вопрос.

## Минимальный пример

Используется пример из поднабора HaluMem Memory Conflict, case 001:

> Did Martin officially begin his retirement on June 1, 2028?

Эталонные свидетельства показывают, что 1 июня 2028 года Martin начал
sabbatical (саббатикал), а не retirement (выход на пенсию).

### Строгий временной поиск

При строгой временной фильтрации свидетельство про 1 июня исключается,
так как считается находящимся вне временного среза.

В результате найденный контекст остаётся непротиворечивым, но в нём
недостаточно информации для уверенного ответа на вопрос.

### Поиск с учётом типа вопроса

Query-aware retrieval (поиск с учётом типа вопроса) возвращает релевантный
факт вне временного среза:

Martin officially started his sabbatical on June 1, 2028.

В фиксированной версии AutoJudge evaluator v2 этот контекст был оценён как:

- consistency_status: consistent
- conflict_type: none
- out_of_slice_evidence: relevant
- missing_required_evidence: false
- supports_answer: true

Это показывает, что сам по себе признак «факт находится вне временного
среза» недостаточен для оценки его полезности: такой факт может быть
необходим для правильного ответа.

## Развитие протокола оценки

### Первая версия с динамическим набором оценщиков

Изначально PoolGenerator создавал новый набор judges (оценщиков) для каждой
retrieval policy (политики поиска).

Из-за этого сравнение было методологически некорректным: одновременно
менялись и способ поиска, и сам набор оценщиков.

### Фиксированный evaluator v1

После этого был зафиксирован один и тот же набор оценщиков:

- CONSISTENCY_JUDGE — проверка непротиворечивости;
- TEMPORAL_JUDGE — проверка временных отношений;
- EVIDENCE_JUDGE — проверка достаточности свидетельств;
- OUT_OF_SLICE_JUDGE — оценка фактов вне временного среза;
- FINAL_AGGREGATOR — итоговое объединение оценок.

На этом этапе обнаружилось, что reference evidence (эталонные свидетельства)
иногда смешивались с retrieved evidence (фактами, реально найденными методом),
а вопрос мог ошибочно восприниматься как утверждение.

### Фиксированный evaluator v2

Во второй версии роли данных были явно разделены:

- retrieved memory — факты, действительно возвращённые методом поиска;
- reference evidence — эталонные свидетельства бенчмарка, используемые
  только для проверки достаточности найденной информации.

Дополнительно было явно указано, что query является вопросом, а не
фактическим утверждением и поэтому не может сам по себе вступать в конфликт
с найденными фактами.

## Текущий статус

Прогон v2 пока завершён частично из-за ограничения OpenRouter API.

Успешно получены результаты для:

- before_aware;
- flat_bm25;
- query_aware.

Оставшиеся варианты:

- strict_temporal;
- transition_aware.

Их планируется продолжить после восстановления доступного API-бюджета.

## Технические особенности запуска

Для работы в условиях текущего лимита OpenRouter потребовалось:

- ограничить максимальную длину ответа каждого оценщика до 1000–2000 токенов;
- выполнять оценщиков последовательно, а не параллельно, чтобы не превышать
  лимит одновременно выполняющихся запросов.

Локальные изменения AutoJudge, необходимые для такого режима запуска,
сохранены в:

`experiments/autojudge/autojudge_runtime.patch`

Файл `.env` и API-ключи в репозиторий не добавляются.
